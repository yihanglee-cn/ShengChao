## 1. 项目概览

**声潮** 是一款用 SwiftUI + AVFoundation 编写的原生 macOS 无损音乐播放器，主打液态玻璃（Liquid Glass）视觉、动态封面、3D 封面（ONNX 深度估计）、CUE 分轨、歌词下载等功能。

关键特点：

- 目标平台：**macOS 26（Tahoe）及以上**，仅 **Apple Silicon（arm64）**
- 技术栈：SwiftUI / AppKit / AVFoundation / CoreImage + ONNX Runtime（C 桥接层）
- 构建方式：**纯命令行脚本**（`swiftc` + `clang`），仓库内**没有 Xcode 工程文件（.xcodeproj），也没有 Package.swift**

### 项目结构

```
ShengChao/
├── Sources/          # 10 个 Swift 文件 + ort_bridge.c / bridge.h（ONNX C 桥接层）
├── vendor/           # ONNX Runtime dylib（32M）+ cover3d_model.onnx 深度模型（26M）
├── assets/           # 图标生成脚本等资源
├── build.sh          # 构建脚本（编译 → .app → 同步桌面/Applications）
├── make_dmg.sh       # DMG 打包脚本
├── README.md
└── docs/             # 本文档所在目录
```

## 3. 本地开发（命令行工作流）

项目没有 IDE 工程，日常开发直接改源码 + 跑脚本：

```bash
cd /Users/oliver/Documents/ShengChao

# 1. 编辑 Sources/ 下的代码（可用任意编辑器：VS Code / Xcode / vim…）

# 2. 编译 + 生成 .app
./build.sh

# 3. 运行（建议直接跑 build/ 产物，避免反复动系统目录）
open build/声潮.app
```

### 注意事项

- `build.sh` 每次构建会先 `pkill` 正在运行的旧实例，并把产物同步到 `~/Desktop/声潮.app` 和 `/Applications/声潮.app`。开发迭代时建议直接运行 `build/声潮.app`，减少对系统目录的干扰。
- 源码编译目标为 `arm64-apple-macosx26.0`，SDK 为系统当前 macOS SDK（27.0），实测可用。

## 4. 调试

### 4.1 当前方案（无 Xcode，命令行）

```bash
# 用 lldb 启动并附加调试
lldb build/声潮.app/Contents/MacOS/LiquidGlassPlayer

# lldb 内常用命令
#   breakpoint set --file AudioLibrary.swift --line 100   # 打断点
#   run / continue / step                                 # 执行控制
#   print <变量>                                          # 打印变量

# 查看运行日志（print / NSLog 输出）
log stream --predicate 'process == "LiquidGlassPlayer"'
```

### 4.2 推荐方案（安装 Xcode 后，图形化调试）

流程：打开工程 → 选择本机（My Mac）作为目标 → `Cmd+R` 运行 → 打断点调试。

| 能力 | 说明 |
|---|---|
| 断点调试 | 命中断点时 app 界面**暂时冻结**（正常现象），可看调用栈、变量、单步执行、LLDB 控制台（如 `po self`） |
| 边看边操作边调试 | 运行时 app 界面照常显示，可正常点播放/切歌/开 3D 封面，断点命中才暂停 |
| View Debugging | 实时查看界面层级与约束，排查布局问题 |
| Instruments | 边操作边录性能（CPU / 音频卡顿等） |
| SwiftUI Preview | 不启动整个 app，单独预览某个 View 的效果（适合调样式） |

> 注意：**装好 Xcode 后还不能直接打开本项目调试**——仓库里没有 `.xcodeproj`，需要先把项目配成 Xcode 工程（详见第 6 节 FAQ）。

### 4.3 Xcode 安装步骤

1. App Store 搜索 "Xcode" 下载（推荐，自动更新），或到 developer.apple.com 下载；免费。
2. 安装包 10GB+，装完约占用 30GB，先确认磁盘空间。
3. 首次启动 Xcode：同意许可、安装额外组件（等待完成）。
4. 切换命令行工具指向 Xcode：

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

## 5. 构建与打包

### 5.1 构建 app

```bash
./build.sh
```

做的事：清空旧构建 → `clang` 编译 C 桥接层 → `swiftc` 编译 10 个 Swift 文件（链接 SwiftUI/AppKit/AVFoundation/CoreImage，含 ONNX dylib 与 rpath）→ 拷贝 ORT 运行时与模型到 `.app` → 生成图标与 Info.plist → ad-hoc 签名 → 同步到桌面与 `/Applications`。

产物：`build/声潮.app`

### 5.2 打包 DMG

```bash
./make_dmg.sh
```

产物：`build/ShengChao-<版本>.dmg`

### 5.3 已知问题清单（打包前必读）

| # | 问题 | 说明 | 处理 |
|---|---|---|---|
| 1 | 版本号不一致 | `make_dmg.sh` 中 `VERSION="1.0.0.0"` 是硬编码；`build.sh` 的 Info.plist 写 `1.2.1.0`；git 历史里已有 `ShengChao-1.2.2.0.dmg` | 打包前统一版本号 |
| 2 | 缺 Python Pillow | `make_dmg.sh` 生成 DMG 背景图依赖 PIL，当前机器未安装 | `pip3 install pillow` |
| 3 | Finder 权限弹窗 | `make_dmg.sh` 末尾用 AppleScript 布置 DMG 图标位置，可能弹出 Finder 权限请求 | 属正常现象，允许即可 |
| 4 | `/Applications` 写权限 | `build.sh` 同步到 Applications 需要写权限，无权限时脚本会自动跳过 | 非阻塞 |

## 6. 常见问题（FAQ）

### Q1：装好 Xcode 后，能直接打开一个 app 来调试吗？

方向对，但有前提：**仓库目前没有 `.xcodeproj` 工程文件**，Xcode 不能直接"打开一个文件夹"调试，需要先把项目配成 Xcode 工程。两种配法：

1. **生成 xcodeproj（推荐）**：一次性配置好所有细节——10 个 Swift 文件、`ort_bridge.c` 编译、`libonnxruntime.1.dylib` 链接（含 rpath）、`cover3d_model.onnx` 拷进 Resources、Info.plist 等。之后在 Xcode 里直接运行与断点调试，不再依赖命令行。
2. **手动新建 macOS App 工程再拖文件**：可行，但容易漏配置（尤其 ONNX dylib 的 rpath 和模型拷贝），漏了会启动即闪退，排查成本高。

### Q2：Xcode 可以自己先下载吗？

可以。App Store 搜索 "Xcode" 下载即可（免费，推荐）；或用 Apple ID 登录 developer.apple.com 下载。注意安装包体积较大（10GB+，装完约 30GB）。

### Q3：调试时能边看到界面、边操作、边调试吗？

可以，这是 Xcode 的标准调试体验：

- 正常运行时 app 界面照常显示、可正常操作，Xcode 后台挂载；
- 断点命中时界面暂时冻结，可在 Xcode 查看调用栈/变量、单步执行、LLDB 命令；点"继续"后界面恢复；
- 另有 View Debugging（界面层级）、Instruments（性能录制）、SwiftUI Preview（单独预览视图）等辅助能力。

### Q4：为什么这个仓库的开发者没有用 Xcode？

从仓库证据看（`.gitignore` 忽略了 `xcuserdata/`、`.xcuserstate`，但**没有忽略 `*.xcodeproj`**），作者本地大概率用过 Xcode 等编辑器，但**有意只提交"源码 + 构建脚本"，不带工程文件**。纯命令行脚本构建的典型动机：

1. **仓库干净、diff 友好**：`.xcodeproj` 是机器生成的复杂文件，易冲突；`build.sh` 里一张源码清单一眼看懂。
2. **可复现、不挑版本**：任何装了 CLT 的 Mac 都能一条命令编译，不依赖工程文件格式，也方便接 CI。
3. **构建快**：直接 `swiftc` 编译，省掉工程解析/索引开销。
4. **依赖就手**：ONNX Runtime 直接 vendored，脚本拷贝即可，无需 SPM/CocoaPods。

代价：牺牲了图形化调试体验（断点 GUI、自动补全、Instruments）。

诚实说明：无法确知作者当时的真实意图（也可能本地有一套未提交的 Xcode 工程），但按仓库现状，最合理的解释是**面向命令行构建与发布设计**。装 Xcode 补工程属于"开发友好"升级，两者不冲突：`build.sh` 继续负责出正式包，Xcode 工程负责日常调试。
